# Challenger Hub Native — focused UX/UI review (2026-10-24)

## Scope and evidence

Reviewed the project source, representative retained Native Focus/Orbit screenshots (Discover, Results, Dossier, Managed and Activity), and the already confirmed Windows Chris PdfCraft first-install journey. The review uses the relevant existing Workspace Cursor role guidance: UX Researcher, UX Architect, UI Designer, UI Finish-Gate Reviewer, Accessibility Auditor, Section 508 Accessibility Specialist, Workflow Architect, Brand Guardian, Behavioral Nudge Engine, and Product Manager. These are design-review instructions; this document does **not** claim autonomous subagents, real participant interviews, a screen-reader session, or formal accessibility certification.

The actual journey is **Find → Compare → Inspect official source → Review release → Consent → Install → Use**. Prioritize failures that keep someone from completing this journey, not hypothetical infrastructure or cosmetic redesign.

## Acceptance checks

1. **Data policy**: review-route filter derives from the existing Node `reviewedSource` validator applied to the actual adapter manifest for the current OS/CPU, then validates IDs against the Rust catalog; research entries and non-allowlisted managed apps never become direct-install candidates. `managed:pdfcraft` is offered **only on Windows x64**. Curated source eligibility does not promise a compatible official release or digest.
2. **Search behavior**: original search/domain filters keep their semantics; enabling review-only filters the visible result list and resets pagination, disabling restores every category. Opening a result, going back and clearing the filter must not lose the query. Empty filtered results explain how to return to full catalog.
3. **Trust**: the filter does not download, install, link an untrusted source or change explicit approval. The exact version, asset, SHA-256 and destination are still shown only after official release review.
4. **Keyboard manual QA (still required)**: on **Chris Windows Session 1** navigate by Tab from search to a result row, Enter to open dossier, Tab to Review, Enter to request read-only review, Tab to consent, Space to toggle; only approve/install real software in the user's explicit interactive action. Check focus visibility, disabled behavior, cancellation timing, and that focus does not become trapped.
5. **Assistive-tech manual QA (still required)**: confirm reading order, labels/roles/checked state, and dynamic progress announcements with a Windows screen reader. Compiling Slint accessibility properties does **not** prove screen-reader operability.

## Decision

The first cross-check found 152 curated sources but only **14 pinned adapters**; the new read-only `routes` protocol exposes the true OS-specific subset (currently **8 on macOS ARM64**). If this policy is absent, the UI fails closed to zero in-app review routes while retaining catalog browsing. The immediate product wins are **truthful review-route discoverability** and **keyboard operation for primary decisions**. Do not turn the deferred typography or rare crash-recovery edges into new workstreams without a real user-facing failure. Keep PR #28 Draft and do not replace Production or reinstall PdfCraft on Chris solely to run this review.

## Real Windows Chris Session 1 accessibility probe (2026-10-24)

Using an ephemeral, least-privilege, InteractiveToken scheduled task under `CHRIS\\Chris` in Windows **Session 1**, we opened the current native CI preview of commit `35b7e15` in a separate QA folder (no installation or SYSTEM execution). The window appeared at 1226 x 844 pixels and was screenshotted. Windows UI Automation identified the **Challenger · Focus Native Preview** top-level window, but reported **zero descendant accessibility elements**. The earlier source-level `accessible-role` additions could not function as a screen-reader tree because `slint` was compiled with `default-features = false` and omitted Slint's `accessibility` feature (which ordinarily pulls in AccessKit). That feature is now enabled in the native host Cargo manifest; corresponding dependencies are locked for repeatable cross-platform builds.

A keyboard SendKeys probe was attempted under the same interactive user, but the foreground-window safety check rejected the sequence before any keys were sent; another application held focus. Do **not** present this as a passed keyboard test. Task Scheduler probe tasks were deleted afterwards. Verify the new Windows CI build exposes nonzero accessibility descendants, then confirm keyboard control under foreground in a non-disruptive way. Testing accessible roles/names via UIA is not the same as confirming Narrator's actual spoken output.
